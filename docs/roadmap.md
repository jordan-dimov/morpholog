# Morpholog: Roadmap

Status: operational. This document is what the project is *doing next*. It is forward-looking and lower-stakes than [`scope-and-ambition.md`](scope-and-ambition.md) (which fixes what Morpholog is *for*) and [`runtime-semantics.md`](runtime-semantics.md) (which fixes what the runtime *means*). When this file and design-history disagree, design-history is the historical record; this file is intent.

The "forced by a worked example" discipline binds **kernel and IR primitives**: a new `Prop` / `ValueExpr` / `Stmt` / `Value` variant earns its place only when an example needs it, never speculatively. That is where unconstrained growth is dangerous, and the bar stays high. It is *not* a brake on everything else - tooling, new worked examples, performance work, legibility surfaces, and product completeness move as soon as the direction is clear, not only when an example forces them. The bar for *adding to the language* is deliberately higher than the bar for *building around it*. This is intent, not a wish list.

## Status today

The kernel, PG adapter, CLI, polling outbox worker, and the worked examples are all in good shape. The parser arc is closed and the examples are `.morph`-canonical, round-trip-coupled to the formatter. The language arc's first rungs have landed (`define`, claim disciplines, the lint tier, source-located diagnostics). The embedder contract is pinned end to end - codecs, schemas and the manifest, the outcome envelopes, batch import, the outbox lease protocol, and the generated Python client that makes the whole contract travel in the binary ([`embedder-integration.md`](embedder-integration.md)); a real external embedder drives a governed trade lifecycle through it, and its friction is a standing source of forcing pressure. The value vocabulary covers time and units where examples forced them; local time and unit conversions enter as claims, never as runtime lookups.

That is all this section says, by rule: **shipped work leaves this file**. What Morpholog does is the [README](../README.md)'s job; what forced each piece and why is [`design-history.md`](design-history.md)'s; this file holds only what comes next.

## The arcs

The forward picture is a set of arcs over one IR - the language arc, the kernel arc, and the verification arc - each a different reading of the same semantic truth the kernel already evaluates and renders. None changes the constitution; each deepens what the existing thesis delivers. The forcing discipline holds throughout: kernel and surface primitives still arrive with the example that forces them; the arcs name the direction, not a backlog.

**The language arc - doctrine into declarations.** `define` (landed) named the conditions; **claim disciplines** (landed) put the append-only / retractable-pointer / lineage trichotomy and structural uniqueness on the predicate declarations, lowered to generated invariants or enforced statically. The metadata makes the gate-vs-invariant doctrine machine-checkable; the lint itself rides with the `--strict` layer. The remaining rung is **parametric patterns** (predicate-parameterised rule templates - restatement, standing, the cross-example idioms as artifacts), awaiting a worked example that genuinely reuses a pattern across domains rather than echoing its shape.

**The kernel arc - the interpreter becomes the spec.** In dependency order: invariant pruning by read/write-set intersection (the walkers exist; days of work when reached); a node-identified IR with a shared fold (ends the per-pass walker duplication; the source-location layer shipped separately - the surface-side `SourceMap` already points validation errors, lints, and runtime rejections at `.morph` declarations and statements, and the shared fold would deepen that to sub-expression granularity); a layered candidate state (base + delta overlay - the base is the pre-state, which dissolves the blocker recorded against the delta-aware rebuild); then the deep one, a **spike compiling the relational core of invariant checking to SQL** executed inside the same SERIALIZABLE transaction. That single mechanism would subsume argument-sensitive scoped loading (the compiled WHERE clause is the argument-sensitive footprint), narrow the SSI read footprint the contend bench measures, and stop commit latency scaling with in-scope state - with the sync kernel retained as the executable specification and a differential-test harness over the worked examples as the correctness argument. One spec requirement recorded up front: the compiled residual checks must be *case-bound* (inconsistency-tolerant, per [`prior-art.md`](prior-art.md)) - rule-version adoption and exception claims mean commit-time checking cannot assume a globally clean history, only that the new write introduces no fresh violation. Spike and measure against the bench before committing to it.

**The verification arc - from explaining to proving.** `explain` answers "why not"; `inspect guarantees` and `controls` answer "what is forbidden and what must be true first"; `inspect coverage` (the arc's opener, landed - see [`design-history.md`](design-history.md)) answers "which rules have ever actually done work" over the replayed audit log. The next tiers ask what the tooling still cannot see: **static vacuity** (an antecedent that CANNOT bind under the declared vocabulary - the offline-oracle tier) and a **rejection log** (the substrate that would upgrade coverage's `fired` to `constrained`: how often a rule actually refused a proposal); the **gate-protection map** (which gate protects which invariant, syntactic subsumption first - the deeper control-matrix tier already named below); and, furthest out, **bounded checking offline** (invariant mutual satisfiability, dead transformations, unreachable-without-claim questions) - an explicit revisit of the no-model-checker non-goal, never in the runtime, under the Cedar-style decidable-fragment discipline [`prior-art.md`](prior-art.md) already endorses. The same machinery is the road to bounded why-not (abduction): the repair-plan tier of the explanation engine, and the engine of the propose-refuse-repair loop the README promises for untrusted proposers.

## Imminent

The prior art and influences behind the directions below live in [`prior-art.md`](prior-art.md). That file is possibility pressure; this one is sequencing.

- **The remaining lint occupants.** The lint tier exists (hints on stderr, `--strict` promotes; the gate-vs-invariant lint is its first occupant). Still to add: unused predicate / intent declarations, `sum(x | body)` where `x` doesn't appear in `body`, unused transformation parameters, fuzzy "did you mean `MayApprove`?" suggestions on an `Undeclared` reference.

- **Remaining legibility surfaces.** The explanation-engine doctrine stands - deterministic template rendering over the IR and trace, never natural-language generation - and its shipped tiers (`explain`, `inspect guarantees`, `inspect controls`, source-located diagnostics) are recorded in [`design-history.md`](design-history.md). Still to build: `inspect transformation --graph` (the body as a pre/post dependency DAG); subject-flow profiles (clusters where the same `Subject`-kind position recurs); a deeper control matrix pairing each gate to the invariant it protects and naming the failure mode each prevents. All derive statically from the parsed programme; none adds IR primitives. Full multi-step path-finding is bounded model checking, deferred; predicate-kind annotations were considered and deferred - the classification is largely inferable from structure.

## Performance, when forced

The bench measures the curves that would force work here; the numbers below are the current readings (full detail in `crates/morpholog-bench/README.md`). Nothing here is forced today.

- **Single-propose scaling is linear, and the kernel is not the bottleneck.** ~1.6s per commit at 100K in-scope claims and ~1.5s for a 100K-transition replay are dominated by load + PG IO, not kernel work. Both are intrinsic to re-reading and re-indexing the full in-scope claim set each transition; the cure is materialisation, not micro-optimisation.
- **Retraction-heavy replay stays linear.** The `as-of --retract-fraction K` axis confirms it: a 50%-retract log replays in the same linear time as an asserts-only one (the `ReplaySet`'s retract is amortised `O(1)`). This was the measurement to take before sizing any snapshot/lattice work - and it says that work is **not forced**. The likely shape when it is: a checkpoint table materialising the live claim set every K transitions, plus a delta-replay path resuming from the nearest checkpoint. That is plain-PostgreSQL application logic - state-at-T is a stateful fold over assert/retract, not a time-bucket aggregate, so *not* something a TimescaleDB continuous aggregate could express.
- **Concurrent proposals on a shared predicate footprint anti-scale, and value-level partitioning does not fix it.** The `contend` scenario shows the SERIALIZABLE 40001 retry rate climbing roughly linearly with worker count while throughput falls: posts that read a predicate and write into it serialise under SSI. Crucially, the `--periods` sweep shows that sharding the writes by value (a private period per worker) leaves the retry rate flat - because `load_state` reads the whole predicate, not a value sub-range, so the read/write footprints still overlap. The `--disjoint` sweep confirms the positive half: giving each worker its own *predicate* roughly quarters the wall-clock and more than halves the retry rate. So the lever is disjoint predicate footprints (already exploited by predicate-scoped loading) or batching, not value-level sharding of one aggregate. The residual contention even when fully predicate-disjoint is consistent with PostgreSQL's predicate-lock granularity (the adjacent `Bench_*` keys likely share an index page) rather than logical overlap; confirming the mechanism would need a physical-layout control. This is also the measured 40001 rate the substrate question below requires.
- **Throughput levers, when concurrency on a hot predicate is forced.** The unit of concurrency is the read footprint the runtime loads, not the business value - so the levers, in increasing depth, are: *batch* the contending writes into one governed transition (one read-set pass for many entries, the natural shape for import / auction / settlement files); model *bounded aggregate claims* (`AccountBalance`, `EntryBalance`) so a transition reads a few aggregates instead of every base line (O(touched aggregates), not O(all lines)); *argument-sensitive scoped loading* - narrowing `load_state` to the predicate slice a transition needs (`JournalLine where period = p7`) rather than the whole predicate, which requires static read-set extraction with runtime parameter substitution, a real feature rather than a DB index; and *key-sliced write routing* - serializing same-footprint writes into one queue before they reach PostgreSQL eliminates hot-key 40001 at the gateway (the deterministic-concurrency literature's move, [`prior-art.md`](prior-art.md)), but needs a resident process, so it arrives with a `morpholog serve` if one is ever forced; until then it is embedder-side guidance. None is forced until a real workload needs the throughput; the bench's `contend` axis is where that pressure would first show.
- **TimescaleDB for the audit log - candidate substrate enhancement, when real scale forces it.** `morpholog.audit` is append-only and time-ordered, a natural hypertable on `committed_at`. Two wins would be real at multi-gigabyte scale: chunk exclusion for as-of window queries, and columnar compression of cold chunks (the repetitive-key JSONB payloads compress well, and compressed-chunks-are-read-only suits an immutable ledger - the strongest reason to reach for it, since the target domains produce GB-scale audit lakes). Hard constraints, because this touches the correctness substrate: single-node only (distributed hypertables drop cross-node `SERIALIZABLE`, non-negotiable, and are deprecated upstream regardless); the `transition_id` primary key must become composite with the partition column, so the as-of lookup path needs re-checking; and SSI behaviour across chunks (predicate-lock granularity, 40001 rate) must be *measured* on the partitioned shape, not assumed. It does not replace the checkpoint work above. Adopting it would be an explicit revisit of the locked PG-only substrate floor. Timescale's analytics primitives stay on the BI side, outside governed reads. Revisit only when the bench surfaces a real storage or replay problem on a real workload - not before.
- **The subprocess CLI tax is low; a long-lived run-worker is not forced.** `scripts/embedder_latency.sh` times one `morpholog run` end-to-end at single-digit milliseconds (~3ms spawn + parse + validate, plus ~6ms connect + propose + commit against a small ledger) - on the order of 100 governed transitions per second, single-threaded. That is comfortable for the lifecycle events the governed core exists for (capture, confirm, settle, approve) and for admin / audit flows. A long-lived worker (load + validate once, warm pool, HTTP or socket) earns its place only when a genuinely high-frequency path needs it - and the doctrine keeps high-frequency analytical paths out of the governed core regardless. The propose component grows with in-scope state as the `write` scenario measures; the spawn / parse / validate floor does not.

## Operational completeness

The hardening real deployment needs. Not language growth and not gated on a worked example - these move as Morpholog approaches its first production deployment. Listed, not frozen.

- **Worker supervisor.** The polling outbox worker exists and ships a `StdoutDeliverer`. Missing: a supervisor running multiple workers under restart-with-intensity, with crash isolation between deliverers.
- **Per-target circuit breakers.** A delivery target that misbehaves should be ring-fenced (back off, alert, eventually quarantine), not continue eating the worker's loop indefinitely.
- **HTTP-aware deliverer.** Once a worked example actually sends an outbox intent over the wire, an `HttpDeliverer` with the right retry/idempotency semantics.
- **Parser-side input-depth guard.** `Program::validate` already rejects expression and `for`-statement nesting past a fixed depth, so over-deep IR cannot exhaust the stack in `propose` - the teeth behind "validate untrusted IR before proposing it". The `.morph` parser has no equivalent guard: a pathologically nested source file could overflow the recursive-descent parser before it produces any IR. Deferred because in v0 you author your own `.morph` files; forced once `parse` ingests source from an untrusted origin.
- **The embedder surface grows by forcing only.** The pinned contract and the generated Python client live in [`embedder-integration.md`](embedder-integration.md); what remains is whatever the next real embedder forces. Already visible on that horizon: a TypeScript client and an OpenAPI surface (each waits for the embedder that needs it), and the generated client's kind floor (Duration / Collection models arrive the same way).
- **Tamper-evident audit (a Merkle history tree).** `morpholog verify` already detects an edit that leaves the claims table and the audit log disagreeing; a *coordinated* edit of both is what tamper evidence addresses. The design intent is a history tree rather than a naive hash chain ([`prior-art.md`](prior-art.md)): logarithmic inclusion proofs ("this transition is in the log") and consistency proofs ("today's log extends last quarter's") are what let a regulator verify an exported **evidence pack** offline - the portable, independently-checkable account of one subject's history that the external embedder has already asked for. Inclusion and consistency prove authenticity and append-only growth, not subject completeness: a subject-complete pack additionally needs a subject-indexed commitment, or a deliberately narrower claim. Key rotations and revocations enter the ledger as first-class claims, judged at signing time.
- **A SQL views generator.** Analytics and BI tools want governed state in their native tongue. The answer that keeps the BI engine out of the kernel: emit plain `CREATE VIEW` statements over the claims table from the declared predicate and derived-claim vocabularies - read-only by construction, regenerated when the model changes, queryable by anything that speaks SQL. The read-side complement of `morpholog schema`.

## Language affordances awaiting a worked example

Each lands when an example actually demands the shape. None are pre-decided.

- **Higher-order authority / predicate-pattern matching.** *One* authority claim governing a *family* of transformations, instead of one per kind. The declared predicate vocabulary now provides a metadata home; the shape itself still needs a worked example.
- **Parametric patterns.** Predicate-parameterised rule templates, instantiated explicitly and expanded at load - the restatement triple, the standing pattern, the cross-example idioms shipped as artifacts instead of READMEs. The rung after claim disciplines on the language arc; it waits for the disciplines to prove the lowering-plus-metadata shape, and for a worked example that genuinely reuses a pattern across domains rather than echoing its shape.
- **Effective time as a separate axis.** As-of gives knowledge time. Effective time - the day a contract becomes binding, the period a posting reflects - is expressible as ordinary claims; combining the two gives bitemporal addressability without `valid_from`/`valid_to` schema columns.
- **Validity windows + repair transitions + exception claims.** First-class typed claims that mark an admitted assertion as in-repair, contested, or quarantined, with audit standing. No bypass flags ever.
- **Materialised derived claims.** Reports are recomputed on demand today. For long audit logs and frequent queries, materialised snapshots become forced - with invalidation modelled as ordinary claims, not as cache machinery.
- **Migrations framework.** A small one. The schema is hand-written today; with multiple deployments and an evolving claim vocabulary, a migrations story will be forced. The shape should be claim-shaped (migration as transformation, schema version as admitted claim).
- **Civil-date arithmetic.** Time arithmetic now exists where the laytime example forced it: exact instants (`Timestamp`) and exact spans (`Duration`), with instants shifting by spans, differencing into spans, and spans summing and capping. What remains deferred is arithmetic on *civil dates* - adding a span to a `Date`, the length between two dates - which is calendar arithmetic (month lengths, leap days) and awaits a worked example that needs it.
- **Port-local time as admitted claims.** The laytime example's next stage: local calendar days (the 25-hour fall-back day, "weather working days") entering as claims from an external calendar authority - `PortDay(port, local_date, starts_at, ends_at, tzdb_version)`-shaped - never as a runtime tzdb lookup. The forcing argument is replay determinism; the principle is that external interpretive knowledge enters as claims, not hidden runtime assumptions. Statement-of-Facts correction after a settled demurrage claim arrives in the same stage.
- **Unit conversions as claims.** Units themselves shipped (the laytime example's cargo tonnage and demurrage money forced `Decimal[t]` / `Decimal[USD]` - contractual labels on exact decimals, same-unit-only algebra, scaling, ratios). What remains deliberately out is everything relating one unit to another: conversion factors, FX rates, market-convention tables. Those are domain knowledge with provenance and time (whose table? as of when?), so they enter as supersedable admitted claims when an example genuinely needs one - never as kernel constants. No compound units and no unit-producing arithmetic until a worked example argues otherwise.
- **`morph fmt` (canonical formatter as a CLI).** The formatter exists in `morpholog-core::format` and is coupled to the parser by the round-trip property test. A CLI front-end (`morpholog fmt <file.morph>` or `--check` mode) lands when a project's worth of `.morph` files starts to feel like editorial drift; not before.
- **Integration / external-compute provenance.** The same primitive (claims) reaching the system's edges: external-computation results admitted as provenance claims, outbox intents acquiring delivery/acknowledgement claims, and actor authority extending to delegated and external actors. The longest-horizon direction; deliberately unspecified in detail until the embedder forces a concrete shape.

## Deliberately out of scope (revisit only with explicit reason)

The doctrinal floors - no entities/classes/services/ORM, no workflow engine, no arbitrary computation inside transformations, no BI engine, no solver runtime, no ad-hoc query DSL, no bypass flags ever - all hold here; they and their reasons live in [`scope-and-ambition.md`](scope-and-ambition.md)'s Non-goals and are not re-listed. The deferrals specific to the operational plan:

- No self-hosting. Morpholog governs business state; the compiler is Rust.
- Tree-sitter / LSP grammars: the parser is the forcing pressure. Deferred until an authoring workflow puts real demand on them.

## How to read this file

If something appears on the "awaiting a worked example" list, that's a *deliberate* hold, not a TODO. The project's central discipline is that kernel primitives arrive alongside the example that forces them; reading the list as a backlog defeats the discipline.

When something ships, it leaves this file - the README says what Morpholog does, [`design-history.md`](design-history.md) says what forced it. Moving an item from "awaiting" to "imminent" goes through the same review/PR loop as code changes. The roadmap moves; the doctrine in [`scope-and-ambition.md`](scope-and-ambition.md) does not.
