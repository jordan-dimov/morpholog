# Morpholog: Roadmap

Status: operational. This document is what the project is *doing next*. It is forward-looking and lower-stakes than [`scope-and-ambition.md`](scope-and-ambition.md) (which fixes what Morpholog is *for*) and [`runtime-semantics.md`](runtime-semantics.md) (which fixes what the runtime *means*). When this file and design-history disagree, design-history is the historical record; this file is intent.

The "forced by a worked example" discipline binds **kernel and IR primitives**: a new `Prop` / `ValueExpr` / `Stmt` / `Value` variant earns its place only when an example needs it, never speculatively. That is where unconstrained growth is dangerous, and the bar stays high. It is *not* a brake on everything else - tooling, new worked examples, performance work, legibility surfaces, and product completeness move as soon as the direction is clear, not only when an example forces them. The bar for *adding to the language* is deliberately higher than the bar for *building around it*. This is intent, not a wish list.

## Status today

Shipped work leaves this file. What Morpholog does is the [README](../README.md)'s job; what forced each piece and why is [`design-history.md`](design-history.md)'s; this file holds only what comes next.

## The arcs

The forward picture is a set of arcs over one IR - the language arc, the kernel arc, the verification arc and the enforcement arc - each a different reading of the same semantic truth the kernel already evaluates and renders. None changes the constitution; each deepens what the existing thesis delivers. The forcing discipline holds throughout: kernel and surface primitives still arrive with the example that forces them; the arcs name the direction, not a backlog.

**The language arc - doctrine into declarations.** `define` (landed) named the conditions; **claim disciplines** (landed) put the append-only / retractable-pointer / lineage trichotomy and structural uniqueness on the predicate declarations, lowered to generated invariants or enforced statically. The metadata makes the gate-vs-invariant doctrine machine-checkable; the lint itself rides with the `--strict` layer. The remaining rung is **parametric patterns** (predicate-parameterised rule templates - restatement, standing, the cross-example idioms as artifacts), awaiting a worked example that genuinely reuses a pattern across domains rather than echoing its shape.

**The kernel arc - the interpreter becomes the spec.** Invariant checking compiles to SQL inside the proposal's own SERIALIZABLE transaction, bounded to the cases a transition touches, with the sync kernel kept as the specification and a differential test holding the two together ([`design-history.md`](design-history.md) has the measurements and the path there). What remains: growing the compiled fragment by forcing example (`pre`, time arithmetic, and sums anywhere in a scope, where orderings already go; decimal and quantity arithmetic compiles), each form carrying its parity bill; and a node-identified IR, which would deepen source locations from statements to sub-expressions (the shared walk every collector descends through already exists; identity waits for the first consumer that needs to name a sub-expression).

**The verification arc - from explaining to proving.** `explain` answers "why not"; `inspect guarantees` and `controls` answer "what is forbidden and what must be true first", and `controls` now also draws the gate-protection map - which gate front-loads which invariant, a syntactic correspondence through shared positive predicates, never a proof of entailment (see [`design-history.md`](design-history.md)); `inspect coverage` (the arc's opener) answers "which rules have ever actually done work" over the replayed audit log, and with the rejection log landed, "which rules have demonstrably refused" via the `constrained` verdict. The next tiers ask what the tooling still cannot see: **static vacuity** (an antecedent that cannot bind in any state the ledger can hold - the offline-oracle tier; note the shipped unsupplied-antecedent and governing-selection lints are *not* this - each is a shape-level authoring smell that says nothing about persisted or historical state - a true vacuity proof needs an enforced closed-world lifecycle or history context); and, furthest out, **bounded checking offline** (invariant mutual satisfiability, dead transformations, unreachable-without-claim questions) - an explicit revisit of the no-model-checker non-goal, never in the runtime, under the Cedar-style decidable-fragment discipline [`prior-art.md`](prior-art.md) already endorses. The same machinery is the road to bounded why-not (abduction): the repair-plan tier of the explanation engine, and the engine of the propose-refuse-repair loop the README promises for untrusted proposers.

The verification arc's furthest reading turns the evaluator **backward**: it scores a hypothesis against history instead of gating a proposal. Two rungs have landed. `evaluate` replays the log under a candidate programme that is not deployed and reports, per candidate invariant, the admitted commits it would have refused; it is a sibling of `coverage`, not a reuse, since a committed rule held on every transition and a candidate was never enforced, so the signal is where history violates it. `rehearse` re-decides every committed proposal under the whole candidate through the ordinary kernel, gates and all, against the state the audit rows before it build, and its contract says that this prefix is the order of effects, not the snapshot a concurrent writer saw. The overfitting guard is in (`evaluate --train-until`: one continuous replay, per-slice attribution, offline packs split identically). Still open: the counterfactual timeline (#402: a corrected fact, candidate-evolved state, a historical programme bundle); many candidates in one pass (#194); definition fitness; and a transition-relational semantics for `pre(...)` candidates, since scoring covers state invariants only. What stays outside the kernel by design: the proposer, the search that recombines candidates, and the labels (known-bad, known-clean, corrected-later) and weighting that turn a counterfactual into a judged score. Morpholog is the deterministic, explainable scorer, which is the whole point where a black-box score is inadmissible, and the survivors a human accepts become governed invariants with provable lineage. Any value-language growth discovery pulls forward (ratios, windowed aggregates) arrives under the usual discipline: each operator with the discovered rule over real data that forces it, never a speculative statistics algebra.

**The enforcement arc - from governed decisions to an unavoidable governed path.** The other arcs assume the proposer reaches governed state only through Morpholog. This one asks what an untrusted proposer can still do around it: write governed state some other way; choose another rulebook; speak another principal's name; reach the consequential external capability directly; or leave an action at the outside system that nothing here records. Four standings name how far a deployment has gone, and each is a property of the deployment as much as of the runtime. *Advisory*: Morpholog evaluates and records, and another route to the state exists. *Record-enforced*: the governed tables are writable only through the runtime's own role (the least-privilege roles `init` provisions), every commit names the programme that admitted it (the model hash), and an armed actor is asserted only by the login granted it (actor-assertion policy). *Action-custodied*: the credential for the external action is held by an executor that consumes only admitted intents through the outbox lease, and never by the proposer. *Closed-loop*: the outside system's own record comes back in as claims and a derived read reconciles it with what was authorised, so an action that escaped prevention is exposed; the closed-loop execution example is the first rung. What the runtime verifies stops at its own boundary: that the executor alone holds the credential, that the reports brought in are all of them, that no second rulebook is deployed, are the operator's assertions, and the docs say which is which. Still open on this arc: the fixed-model proposal boundary (#475), the constrained executor with deployment-owned intent mapping (#476), production model pinning (#477), and exact-proposal approval (#478). The outbox's side is pinned: a delivery lost to a crash is delivered again as the same intent, with the same idempotency key. The authenticated-authorship arc (#202, #417) is its complement: who proposed, rather than what the proposer could reach.

- **Remaining legibility surfaces.** The explanation-engine doctrine stands - deterministic template rendering over the IR and trace, never natural-language generation - and its shipped tiers (`explain`, `inspect guarantees`, `inspect controls`, source-located diagnostics) are recorded in [`design-history.md`](design-history.md). ## Performance, when forced

The bench measures the curves that would force work here (current readings in `crates/morpholog-bench/README.md`; the measurement rules in `docs/benchmarking.md`). A programme whose rules compile to SQL already commits in flat time and without excess retries on a shared key; the items below concern the rest - rules checked by the in-memory interpreter, replay, and the size of one affected case. Nothing here is forced today.

- **Interpreted commits and replay scale linearly, and the kernel is not the bottleneck.** About 1.5 s per interpreted commit at 100K in-scope claims, and about 1.5 s for a 100K-transition replay, both dominated by loading the in-scope claims rather than kernel work. A single affected case that is itself large costs time in its size on either route. The cure is materialisation, not micro-optimisation.
- **Replay is linear under retraction and revision alike**, so the curve does not force snapshot work. When a workload does (#377: an as-of read on a long history with a small live set), the shape is a snapshot of the live claim set every K transitions plus delta replay from the nearest one, built on the one audit order: plain PostgreSQL application logic, distinct from the Merkle checkpoint, which commits to integrity rather than caching state.
- **Concurrent proposals on a shared footprint conflict under SERIALIZABLE** even when their cases are disjoint, and sharding writes by value does not relieve it, because an interpreted invariant still loads its predicates whole; disjoint predicates do, by about four times. Keyed body reads and their indexes took the retry rate on the pinned classroom workload from 3.4 per commit on v0.0.12 to 0.33 on v0.0.16 (#396 has the lineage). What remains: loading only the cases an interpreted invariant's effective change can touch, and the first proposals on an empty table, which a sequential scan locks whole.
- **Throughput levers, when a hot predicate forces them**, in increasing depth: batch the contending writes into one `transact`; model bounded aggregate claims, so a change reads a few aggregates instead of every line; and key-sliced write routing, which serialises same-footprint writes before they reach PostgreSQL and arrives with a `morpholog serve` if one is ever forced.
- **TimescaleDB for the audit log, when real scale forces it.** The log is append-only and time-ordered, so chunk exclusion for as-of windows and compression of cold chunks would be real wins at multi-gigabyte scale. The constraints, since this is the correctness substrate: single-node only (distributed hypertables drop cross-node SERIALIZABLE); the primary key becomes composite with the partition column; and SSI behaviour across chunks must be measured, not assumed. An explicit revisit of the PG-only floor, and only when the bench surfaces a real storage or replay problem.

## Operational completeness

The hardening real deployment needs. Not language growth and not gated on a worked example - these move as Morpholog approaches its first production deployment. Listed, not frozen.

- **Worker supervisor.** The polling outbox worker exists and ships a `StdoutDeliverer`. Missing: a supervisor running multiple workers under restart-with-intensity, with crash isolation between deliverers.
- **Per-target circuit breakers.** A delivery target that misbehaves should be ring-fenced (back off, alert, eventually quarantine), not continue eating the worker's loop indefinitely.
- **HTTP-aware deliverer.** Once a worked example actually sends an outbox intent over the wire, an `HttpDeliverer` with the right retry/idempotency semantics.
- **Parser-side input-depth guard.** `Program::validate` already rejects expression and `for`-statement nesting past a fixed depth, and evaluation takes only validated programmes, so over-deep IR cannot exhaust the stack in a proposal. The `.morph` parser has no equivalent guard: a pathologically nested source file could overflow the recursive-descent parser before it produces any IR. Before that, it gets slow: measured on 2026-10-03, a body nested 250 parentheses deep parsed in 0.4 s, 1,000 deep in 9 s, and 4,000 deep did not finish in 100 s. Deferred because in v0 you author your own `.morph` files; forced once `parse` ingests source from an untrusted origin.
- **`morpholog serve` - the socket rung above the stdio session.** The resident process exists: `morpholog session` answers propose and the page reads over stdin/stdout with the pinned envelopes, one child per embedder worker, and the generated client wraps it. What remains for a `serve` is what stdio cannot give: a socket or HTTP transport, more than one client per process, correlation ids and concurrent in-flight requests (the session is deliberately lockstep), and the key-sliced write routing above - each waiting for the workload that forces it. The contract is already settled by the session: the same pinned envelopes, a daemon rather than a language-specific in-process FFI (PyO3 / napi), so the one-contract, process-isolation, and polyglot properties survive the transport change. What will NOT arrive with it is transparent transport selection in the generated client: a session's loss leaves a commit outcome unknown, so choosing it is a decision a caller makes deliberately rather than a flag that quietly changes how failure behaves.
- **The embedder surface grows by forcing only.** The pinned contract and the generated Python client live in [`embedder-integration.md`](embedder-integration.md); what remains is whatever the next real embedder forces. Already visible on that horizon: a TypeScript client and an OpenAPI surface (each waits for the embedder that needs it), and the generated client's kind floor - `Duration` models still await an embedder, while `Collection` arguments now have a named forcer (the set-valued-proposal / batch-completeness example under "Language affordances").
- **Tamper-evident audit: the proofs still to come.** Checkpoints, evidence packs (full, window and selective), signed tree heads and RFC 3161 witnesses have shipped. What remains: the OpenTimestamps rung (a pending calendar proof that names no time until upgraded, then a Bitcoin block time - a second witness scheme under the same `witness` entry, forced by an embedder whose pack buyers ask for a witness no single authority controls); the contiguous-range multiproof (a size optimisation over the per-row inclusion form, possibly forced sooner by large windows); and **subject completeness** (inclusion and consistency cannot prove a pack holds *all* of one subject's history - a selective pack proves what it shows, never that the selection is complete; that needs a subject-indexed commitment, or a deliberately narrower claim).

## Language affordances awaiting a worked example

Each lands when an example actually demands the shape. None are pre-decided.

- **Conway's Game of Life - whole-state proposal stripped of business noise.** The margin-call example already proposes a whole set; Conway's Game of Life would be the miniature: not a simulator, but the smallest fully-determined world where a proposer submits a whole successor snapshot and Morpholog admits it only if it is exactly the lawful successor - the same shape, stripped of business noise. A forcing toy for whole-state proposal, if it earns its place.
- **Higher-order authority / predicate-pattern matching.** *One* authority claim governing a *family* of transformations, instead of one per kind. The declared predicate vocabulary now provides a metadata home; the shape itself still needs a worked example.
- **Cryptographically authenticated actors (the attestation arc).** The foundations are in: every durable commit path takes an attested proposal, the audit row records how the actor identity was established, and that lineage is inside the Merkle commitment. Gateway attestation - the mode shipped - is honest about its limit: the PostgreSQL-authenticated role of the proposing connection asserted the actor, nothing more; the actor itself remains an assertion. The remaining rungs, each waiting for its forcing pressure: a canonical proposal encoding with a proposal identity (versioned, byte-pinned - the thing a key signs); authentication-policy and actor-key claims kept deliberately separate (policy must survive the loss of every key - retracting a compromised key locks the actor out, never silently downgrades to gateway mode); an authenticated-presentation record with first-presentation-consumes replay semantics (a lawful rejection then commits the presentation record while committing no governed claims); and signature-mode attestation itself, an Ed25519 signature over the canonical proposal by a key whose authority is an admitted claim resolved as-of, on the keys-as-claims rails the signed-checkpoint work built. Unauthenticated attempts are never attributed to the named actor - a bad signature proves only that someone claimed the name. The forcing example for the signature rungs is the one where a forged actor is the actual vulnerability: two-distinct-person verification is vacuous while a gateway can invent both identities, and multi-writer topologies whose proposers do not trust each other's gateways share the same shape.
- **Parametric patterns.** Predicate-parameterised rule templates, instantiated explicitly and expanded at load - the restatement triple, the standing pattern, the cross-example idioms shipped as artifacts instead of READMEs. The rung after claim disciplines on the language arc; it waits for the disciplines to prove the lowering-plus-metadata shape, and for a worked example that genuinely reuses a pattern across domains rather than echoing its shape.
- **Validity windows + repair transitions.** First-class typed claims that mark an admitted assertion as in-repair, contested, or quarantined, with audit standing. A claim recorded in error has its idiom (an append-only erratum naming the line, rules reading standing through a definition: `examples/24_order_blotter/`); the marks that are not final verdicts wait for the workload that forces them. No bypass flags ever.
- **Materialised derived claims as governed state.** The operational read-cache form has shipped (`morpholog refresh derived` -> `morpholog_read`): a discardable projection whose freshness is operational metadata (model hash, refresh time, and the latest audit transition visible in the refresh snapshot - a marker, not a lossless high-water). What remains deferred is the *governed* form - materialised snapshots whose invalidation is modelled as ordinary claims rather than cache machinery - and the cheaper-refresh tiers the read cache will force when scale demands them (partitioned / incremental / affected-key refresh, then a streaming `enumerate_derived`). The current refresh is exact and full; its scaling boundary is documented in [`design-history.md`](design-history.md). One small operational legibility gap alongside it: a derived view of a stale or mismatched cache reads as empty, which a dashboard cannot tell apart from "no rows" - a companion metadata view (model hash, refreshed-at, latest visible transition, per-predicate row count) emitted beside the data views would let a reader distinguish empty-because-stale from empty-because-nothing.
- **Migrations that reshape.** The migrations so far add a column, a table, an index or drop a constraint, and a recorded version refuses a database behind or ahead of the binary by name. What a migration that reshapes a column or a table looks like, and what it owes the rows it touches, waits for the first one that must.
- **Held back, not sugar: a derived predicate inside an invariant.** `NetPosition(book, net) and PositionLimit(book, limit) implies abs(net) <= limit` is the most elegant form, but it makes read-side derived claims commit-relevant: derivation would run over candidate state inside `propose`, crossing the read-side/commit-side boundary kept on purpose. Its own design question, not sugar. A unit-preserving negation waits for a quantity programme that reads better with it; signed literals stay barred.
- **Convention day counts.** Civil-date arithmetic is in the kernel (`span(P3M)`, date subtraction as actual days), and calendar days enter as claims, which `generate local-days` and `generate business-days` write. What remains outside until forced: convention-specific day counting (30/360 and its cousins), which replaces the actual calendar difference with a contractual counting rule, so each waits for the real contract that forces it and arrives as a parameterised form the way `round(x, quantum)` did, one measured mode at a time; and business-day conventions ("modified following") as reusable `define`s, waiting for the contract that names one. The doctrine stays: a holiday set is data that changes over time, so a runtime calendar lookup would make a decision replay differently once the calendar updates, the same argument that keeps the clock out of the kernel.
- **Port-local time as admitted claims.** The laytime example's next stage: local calendar days (the 25-hour fall-back day, "weather working days") entering as claims from an external calendar authority - `PortDay(port, local_date, starts_at, ends_at, tzdb_version)`-shaped, which `generate local-days` writes - never as a runtime tzdb lookup. The forcing argument is replay determinism; the principle is that external interpretive knowledge enters as claims, not hidden runtime assumptions. Statement-of-Facts correction after a settled demurrage claim arrives in the same stage.
- **Unit conversions as claims.** Units are labels on exact decimals (`Decimal[t]`, `Decimal[USD]`). What remains deliberately out is everything relating one unit to another: conversion factors, FX rates, market-convention tables. Those are domain knowledge with provenance and time (whose table? as of when?), so they enter as supersedable admitted claims when an example genuinely needs one - never as kernel constants. No compound units and no unit-producing arithmetic until a worked example argues otherwise.
- **Spatial values - admission rules that depend on where something is.** Quantity, time, and authority are governed; *location* is not. A point is two opaque decimals today, with no `within` / `contains` / `intersects` the runtime can act on - so "this delivery is only legitimate inside the contracted zone" or "these two land claims must not overlap" cannot be written as admission law. The forcing example is a spatial *gate* (a delivery or policy admitted only if a location lies inside a permitted region - energy bidding zones, catastrophe-zone underwriting) or a spatial *invariant* (no two claims cover overlapping area, the spatial form of no-double-counting that extends the carbon example). It forces a point and region value kind - exact decimal coordinates, no floats in a boundary test - and an in-kernel geometric predicate, evaluated in memory like every other rule and never delegated to PostGIS: a host call during admission would break deterministic replay (the same argument that keeps the clock out of the kernel), so PostGIS, if it ever enters, is a downstream-query concern. And, like timezones and calendars, the geometry must carry or reference an explicit coordinate reference system and region authority as admitted data: the kernel may own deterministic topology (containment, overlap) over geometry it is *given*, never hidden projection, geodesy, or map-version interpretation - those change over time and by authority, so baking them in would make a boundary test replay differently as the map updates. General GIS - distance, routing, projections, spatial analytics - stays out of scope.
- **`morph fmt` (canonical formatter as a CLI).** The formatter exists in `morpholog-core::format` and is coupled to the parser by the round-trip property test. A CLI front-end (`morpholog fmt <file.morph>` or `--check` mode) lands when a project's worth of `.morph` files starts to feel like editorial drift; not before.
- **Integration / external-compute provenance.** The same primitive (claims) reaching the system's edges: external-computation results admitted as provenance claims, outbox intents acquiring delivery/acknowledgement claims, and actor authority extending to delegated and external actors. The longest-horizon direction; deliberately unspecified in detail until the embedder forces a concrete shape.

## Deliberately out of scope (revisit only with explicit reason)

The doctrinal floors - no entities/classes/services/ORM, no workflow engine, no arbitrary computation inside transformations, no BI engine, no solver runtime, no ad-hoc query DSL, no bypass flags ever - all hold here; they and their reasons live in [`scope-and-ambition.md`](scope-and-ambition.md)'s Non-goals and are not re-listed. The deferrals specific to the operational plan:

- No self-hosting. Morpholog governs business state; the compiler is Rust.
- Tree-sitter / LSP grammars: the parser is the forcing pressure. Deferred until an authoring workflow puts real demand on them.

## How to read this file

If something appears on the "awaiting a worked example" list, that's a *deliberate* hold, not a TODO. The project's central discipline is that kernel primitives arrive alongside the example that forces them; reading the list as a backlog defeats the discipline.

When something ships, it leaves this file - the README says what Morpholog does, [`design-history.md`](design-history.md) says what forced it. Moving an item from "awaiting" to "imminent" goes through the same review/PR loop as code changes. The roadmap moves; the doctrine in [`scope-and-ambition.md`](scope-and-ambition.md) does not.
