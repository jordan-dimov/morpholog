28 merges since v0.0.16. The audit log has one order. Every transaction takes one place in it when it writes its first audit row, and every row records what its commit did to the claims table, so replay rebuilds the table exactly even when writers overlapped. A read as of a timestamp follows that order too. Arithmetic is exact: `+`, `-` and `*` return the mathematical result or refuse, where they used to round, and the compiled checks compute arithmetic and builtins in SQL with the kernel's values. A new command, `rehearse`, re-decides every committed proposal under a candidate programme. Two generators write a year of calendar days as proposal rows.

Three migrations are needed, and one of them pauses writers, so read Upgrading before you deploy. The semantics version moves to 4: a receipt decided under 3 reads `not_re_evaluated` from this release's verifier, never a mismatch. No programme hash moves.

## Upgrading

- **Run `morpholog migrate`, with a procedure.** Migrations 026, 027 and 028 are pending for a v0.0.16 database. 026 and 028 add SQL functions and take no lock of note. 027 is the canonical order: it adds columns, indexes and a Merkle pass over the existing history with the database in service, then one cutover that holds every writer while it writes the baseline (measured 3.6 seconds at three hundred thousand live claims and 22 at two million; readers are never held). The install guide's "Running the migration to the canonical order" gives the steps: back up, `migrate --check` for the preflight (legacy rows, estimated preparation and pause, anything that refuses the cutover now), `migrate --prepare` ahead of the window and again just before it, `migrate` in the window, then `audit verify` and `audit checkpoint`. A plain `migrate` with no window does all of it in one run. The cutover refuses a prepared transaction left open or a session the login cannot see, by name; fix that and run it again. Interrupted at any point, `migrate` resumes. A v0.0.16 binary refuses the migrated database as ahead of it.
- **Decisions move: semantics version 4** (#616). `+`, `-` and `*` over decimals and quantities now refuse where they used to round half to even into the digits that fit: `1e-28 * 0.5` was `0`, the largest decimal plus `0.4` was unchanged, and `round` could return a figure that was not a multiple of its quantum. A result that fits is unchanged, digits included, so a rule over ordinary figures decides as before. A transformation whose arithmetic used to round now errors, which `propose` reports as a kernel error, not a rejection. To find them before anyone does: after the migration, run `morpholog rehearse <your programme>` with the programme you serve, unchanged. Read the report as a diagnostic, not a proof. A row reported as `would_error` is a proposal that errors under this binary when re-decided against the audit prefix before it, and under the same programme the arithmetic is the likeliest cause; but the prefix is the order of effects, not the state each original proposal saw while writers overlapped, so a row can also error or differ for that reason, and a row the record cannot replay, an act the programme no longer has or arguments it no longer takes, is `unreplayable` rather than judged. Look at each `would_error` row's reason before concluding anything about it. The known limit: a product of two wide figures, about twenty-eight significant digits in total, refuses where it rounded; rounding the operands first is not the same figure, and a rounded multiplication waits for an example that needs one. Division keeps its rounding rule. Audit rows and receipts stamp the version they were decided under; a verifier on another version says `not_re_evaluated`.
- **Regenerate every Python client** with the v0.0.17 binary. A client pins the binary version, so a v0.0.16 client refuses this binary at its first call. Three contract changes reach existing code:
  - `writer_roles` is gone from `audit()`, `audit_named()` and `audit_checkpoint()`, as `--writer-role` is gone from the binary: the watermark reads the lock table, so it needs no view of other sessions and no assertion of who writes (#632). A call that passed it is a `TypeError`.
  - `deadlock_detected` is a new proposal-row code beside `serialization_failure` (#626): PostgreSQL chose this transaction as the victim of a lock cycle and nothing was recorded. `retriable` is true for both, and `envelopes.RETRIABLE_CODES` is the list. A v0.0.16 client refuses the receipt as an unknown code, which is the safe side.
  - Audit rows written since the migration carry `audit_order`, `act_ordinal`, `ordered_at` and `operations` (#632); the strict models refuse an unknown key by design. The new models: `Ordering`, `Operation`, the rehearsal report family, `ActivationPreflight`, `ReplayIndeterminate`, `ReplayConflict`, `TreeActivationFaulty`. New methods: `rehearse()`, and `migrate(prepare=True)`.
- **Scripts that pass `--writer-role`** to `inspect audit` or `audit checkpoint` fail at argument parsing. Drop the flag; the lossless resume no longer needs it.
- **The tail's rows change shape.** Rows from before the migration are as they were. The migration itself writes control rows at the first order: `morpholog.baseline` chunks, then `morpholog.activate`, each with the attestation `{"mode": "migration"}`. They are not transitions of any programme: coverage, `evaluate` and `rehearse` skip them, and `--as-of` a chunk's id is refused with the record's id to use instead. A projector that dispatches on transformation names sees them once. A fresh database has none.
- **Evidence packs are format 19** (#632). This release verifies format 19 and format 17, which v0.0.15 and v0.0.16 wrote, when every row of a format 17 pack is from before the order. A v0.0.16 verifier refuses a format 19 pack as unsupported. Format 18, which only development builds wrote, is refused by name. Keep old packs with the release that wrote them, or export them again.
- **`audit verify` has a third replay verdict, and it is not corruption.** The report carries two verdicts: the tree verdict, which says whether the log was edited, and the replay verdict, which says whether replaying the log rebuilds the claims table. `consistent` and `divergent` as before, and now `indeterminate`: a legacy history whose replay does not reach the baseline the migration recorded, which two legacy writers overlapping before the order existed can lawfully cause, since their rows were sorted by transaction start. The tree verdict stands on its own; an `indeterminate` replay beside a passing tree means the pre-migration order cannot be told apart from the table, not that anything was changed. Rows written since the migration replay exactly. A `divergent` report now lists `conflicts`, such as a delete of a claim the history never held, which is what to read first. `audit verify-pack` holds a complete-prefix pack to the activation's shape, `activation_faulty` otherwise.
- **`--as-of <timestamp>` needs the primary** (#645). "As of t" is the state after every transition placed in the order at or before t. The reads settle the instant against the orders still held on the connected server, so a standby cannot answer one; a transition id still can. An instant later than the last settled row while a writer is in flight is refused as not settled; retry once that writer finishes. The same holds for `--after` with a transition that is not yet settled. `evaluate --train-until <timestamp>` selects by the same order, and its report is format 6.
- **No programme hash moves.** The twenty-four gallery programmes hash the same under the v0.0.16 binary and this one, checked side by side. The canonical encoding is unchanged.
- **Index plans are unchanged.** Planned with the v0.0.16 binary and with this one, each on its own database, the whole gallery needs the same 371 indexes and 9 statistics objects, by name. The compiled arithmetic adds no seek. Run `morpholog provision indexes --check <programmes>` after the migration as the upgrade sequence says.
- **`check` may newly hint.** `BindOnlyToRetract` (#614): a `bind` whose fields are read by nothing but the `retract` that follows, where the kept fields cover a uniqueness key, can be the pattern form `retract Row(row: row, ..)`, which has always matched and retracted every hit. A `require` keeps the refusal a `bind` gave on no match. A hint fails `check --strict`.
- **Gallery programmes changed.** If you copied one, compare it:
  - example 02 gains replay guards on its two revenue acts and refuses a reused id (#620);
  - example 08 takes one result per screening and refuses a stale result moving the pointer back (#623);
  - twenty-six acts across nine examples that sent a notice and could be accepted again unchanged are now refused, and seven ids or notices that could stand for two records are disambiguated, in 03, 06 and 13 among others (#621);
  - example 24 is new (#612).

## The language

- **Exact arithmetic** (#616). The syntax sheet always promised exactness, and a `sum` that did not fit refused; now `+`, `-` and `*` do the same. `round(v, q)` computes over exact integers and is judged on the multiple it selects: an unchosen candidate or the doubled remainder outside the range is no reason to refuse. Nothing in the surface changes.
- **No new construct.** The erratum (#534) is an idiom: an append-only claim about a claim, `RecordedInError(claim_id, reason)`, naming the recorded line by its own identity, with rules reading the line through a definition of standing. The retract by key (#390) was always there; the syntax sheet shows it now. The generated grid stays in transformation bodies.

## For embedders

- **`morpholog rehearse <candidate.morph>`** (#521), against the database or `--pack`. Every committed proposal is re-decided under the candidate, which is not deployed, through the ordinary kernel: gates, bindings, claims and intents, not only invariants, each against the state the rows before it build in the canonical order. Each row is `same`, `different_delta`, `would_reject` with the first refusing rule, `would_error`, or `unreplayable`; refusals are counted per rule. Recorded draws feed the subject source, so a minted id is the recorded one. Read-only; the `rehearsal_report` envelope is pinned, with the client's `rehearse()`. The log holds admitted history only, so this answers what the candidate would have refused, never what demand there was.
- **One audit order** (#632, #634, #635, #636, #641, #643). `inspect audit` emits rows in `(audit_order, act_ordinal)` order; `--after` resumes losslessly from the lock table's watermark; a direct SQL reader follows the same recipe, which the guide gives. `operations` on each row is what the commit did, `ins`, `del` or `noop`, and replay applies those. The audit pager reads at most one baseline chunk per page, so the live verifier, checkpoint and export stay bounded on a migrated history (measured at two million claims: checkpoint 116 MB, export 49 MB).
- **`migrate --check` and `migrate --prepare`** (#634). `--check` reports the preparation state and an `activation_preflight` with estimated costs and refusals; `--prepare` does everything except the cutover and resumes where it stopped. The client's `migrate(check=True)` and `migrate(prepare=True)`.
- **As-of by time** (#645). `--as-of <timestamp>` on the claims and derived reads, `evaluate --train-until <timestamp>`, and the offline split of a pack all resolve an instant to a prefix of the order that splits no transaction. The train and test slices of a timestamp split are the same live and from a pack.
- **`deadlock_detected`** (#626) in every receipt and error object where `serialization_failure` appears. Submit the same proposal again; the two differ in what to look at when they recur, lock order against overlapping reads.
- **Compiled arithmetic** (#419). Decimal and quantity `+ - * / %`, `abs`, `min`, `max` and `round` compile, through migration 026's SQL functions held to the kernel by a property sweep over every operation. Of the gallery's invariants that ran interpreted under v0.0.16, eleven run compiled now, counted with `check --json` under both binaries. Cost, never meaning: a rule the compiler refuses, such as an arithmetic chain past its SQL budget, stays interpreted, and `check --json` says which.
- **Calendar claims as proposal rows** (#602). `generate local-days` writes a zone's local days, bounds as UTC instants and the tzdb release they were read under; `generate business-days` writes the working days of a holiday list with its authority, version and covered dates. Both take the programme and the transformation the rows propose, fill their fields by name, take every other parameter from `--arg`, and decode every row through the named-argument codec before writing any. The rows go through `propose --batch` per row or `transact --acts` whole; generation admits nothing.
- **The README's front page** (#610) now names the questions the record answers after the gate: would a stricter rule have helped, can a rule be tightened on a live ledger, what did an agent do outside its mandate, with the command or example for each.

## Worked examples

- **24, order blotter** (#612). A cancel recorded by mistake on an append-only blotter: the erratum names the line, rules read standing lines through a definition, and the correction is admitted through the ordinary act.
