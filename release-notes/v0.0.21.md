## Upgrading

Follow the upgrade checklist in `docs/operating.md`: stop every process, back up, migrate, verify the audit, check provisioning, regenerate the clients, and start on the new binary.

- **Run `morpholog migrate`** (032). It adds `compared_branches` to `morpholog.rejections`: a nullable list, checked to be non-empty, that never sits beside `compared` on one row. Older rows read with it absent.
- **Run `provision indexes --check` for every programme.** On a database v0.0.20 provisioned for every gallery programme, nothing is outstanding: all 525 indexes are kept. To read history views through the audit log's index, run `provision indexes --history` once (#909). It is the deployment's choice, and no run prunes it.
- **Regenerate the views** with `generate views`. The view description moves from format 4 to 5. A history view now carries a condition the history index serves, and gains a lookup function per declared key, `<view>_by_<key fields>` (#909). Lookups are granted to no one: grant `EXECUTE` where you grant `SELECT` on the views. A lookup returns its view's row type, so dropping a history view now needs `CASCADE`. A live view is distinct on each key's column (#898); its rows do not change.
- **`check` refuses a little more:**
  - a comparison like `<` of two timestamps in one branch of an `or`, through a definition's parameters (#908). v0.0.20 passed it, and the first decision failed on it;
  - a derived claim's `value` whose name is not the column at its place (#872). v0.0.20 filled the columns in order whatever the names said, so such values landed in the wrong columns. No programme measured had one.
- **A `propose --batch` row with a field the row does not read** gets an `invalid_request` receipt naming the field, and is not proposed (#884). The rows around it run as before. Before, the field was dropped without a word, so `explain_on_reject` in a batch row looked honoured and was not.
- **Regenerate every Python client** with the v0.0.21 binary. A client pins the binary version. What reaches existing code:
  - `Rejected`, `AtomicRejected`, both explanation verdicts, rehearsal rows and rejection rows carry `compared_branches` (#910); an envelope carrying it and `compared` together is refused;
  - an explanation's gate verdict carries `related_parameters` (#882);
  - `ViewDescription` carries `lookups`, in format 5, and `ProvisionReport` an optional `history` entry (#909);
  - `Session.process` is the child a session spawned (#885);
  - `local_days` and `business_days` run the calendar generators and return their rows, ready for `transact` (#887).
- **Gallery programmes changed.** If you copied one, compare it:
  - example 27, the GB gas day, gains renominations, trade nominations, the clock change, and who may do what (#894, #896, #902, #914);
  - example 23 changes only in its comments, but its canonical hash moves with them (#891).
- **Formats:** evidence packs stay format 19, the score report format 6, the rehearsal report format 2. The view description moves from 4 to 5.

## For embedders

- **One entity's history, read through the log's index** (#909). A history view used to expand every audit row's operations. With the index, a whole view reads the audit rows that mention its predicate, and a lookup reads those that mention one entity. On the InvenTree fork's record:
  - the stock history browser tests pass under four workers, in 3.3 to 12.9 seconds, against 10.9 to 27.0 with the index alone;
  - the median history read is 0.44 seconds, against 8.1 with the index alone and 10.5 on v0.0.20, over 4 successful reads;
  - the page bodies are byte-identical.

  Most of the gain needs the host to call the lookups: the index alone took the median from 10.5 to 8.1 seconds.
- **A refused `or` names each branch's figures** (#910). A refusal at an `or` whose branches are each a comparison carries `compared_branches`, one `{op, left, right}` per branch in branch order, and no `compared`. `before <= cap or after < before`, refused at a cap of 10, names `20 <= 10` and `30 < 20`. An `or` with a branch that is not a comparison names none. It appears on the `rejected` envelopes, in `explain`'s verdict and prose, in `rehearse`, and in the rejection log, which `--mentions` searches.
- **A preview names the parameters a refusing gate reads** (#882): `explain`'s gate verdict carries `related_parameters`, as a refusal does.
- **A read of one key of a live view computes that key alone** (#898). On 10,000 orders and 30,000 fills, one order's figure went from about 106 to about 4 milliseconds. Only a comparison with values reaches the key: `= $1`, `= ANY($1)`, `IN (...)`. A join, `IN (SELECT ...)` or `LATERAL` computes every key first, on the generated view as measured (#905). So read a page's keys, then the view by `= ANY` of them.
- **Live or cache per derived claim** (#873). `generate views --derived-source <Derived>=live|cache` chooses one claim's source over the `--derived` default. A claim chosen live that cannot render refuses the run by name.
- **Independent cases on one database can still abort each other** (#912). PostgreSQL tracks serializable reads by index page, and unrelated cases' entries can share pages. The guide now says what makes it worse and what to do: retry. The adapter's tests pin that such an abort is a retryable serialization failure, and that the retry commits.
- **The embedder guide** gains: a figure shared between a rule and a read, and the local date of an instant (#876); that the generated client carries durations and collections (#880).

## The language

- **Live derived views take more of the language:**
  - `max(x | body)` and `min(x | body)` over a decimal position (#881);
  - a sum's target computed from each row, such as `q * price * (1 - d / 100)` (#889), or by a value definition's call (#893);
  - a domain over a condition whose body is an `or` (#877).
- **A key crosses a call and a `forall`'s source** (#870). A value a pattern inside a called condition finds now narrows the reads after the call, and a `forall`'s source narrows its body. A key nesting more than 64 lookups reads whole.
- **One evaluation computes each repeated aggregate once** (#888). Within a gate, an invariant's judgement or a derived claim's rows, a `sum`, `max` or `min` keeps its result for the same values and state. A figure used three times went from a 2.15 to a 0.77 second median.
- **`check` passes an antecedent** that calls a definition calling itself through an `or` (#869). v0.0.20 overflowed its stack.
- **Two parse errors name the rule they break** (#879).

## Rust API

- `render_views` takes a derived source per claim, not one flag (#873).
- `RejectedWithExplanation::new` takes `compared` and `compared_branches` as one pair (#910).
- `RejectionReason::{Invariant, Require, BindNone}`, `RowClass::WouldReject`, `PgProposalOutcome::Rejected`, `PgAtomicOutcome::Rejected`, `GateRejection` and `InvariantRejection` gain `compared_branches`, and `RejectionRow` an optional one (#910). Code that builds them names the new field.
